# Build system measurements

## Bootstrap and executor

On 2026-11-10, five interleaved x86_64 runs compared upstream CMake 4.4.5
bootstrap with the Alpine CMake 4.3.4-r0 package. Each run configured and built
the full CMake source with the P4 toolchain in a new build tree. Input files,
executors, and container images were cached; filesystem caches were warm.
The upstream run included `./bootstrap` and the subsequent `cmake` target.
The Alpine run used the installed APK. Both used the same release and hardening
settings, with Samurai and Ninja distributed across the two bootstrap choices.
Every build completed and reported CMake 4.4.5.

| Bootstrap | Pipeline median | Pipeline range | Peak RSS range | Runs |
| --- | ---: | ---: | ---: | ---: |
| Upstream | 1,233.92 s | 1,190.04–1,384.78 s | 371,596–378,648 KiB | 5 |
| Alpine APK | 633.86 s | 545.21–771.68 s | 368,212–380,280 KiB | 5 |

The Alpine median was 48.6% lower. Paired pipeline differences ranged from
462.24 to 798.18 seconds, with a median of 644.83 seconds. Alpine is selected
because the gain exceeds the 20% threshold and the observed paired spread.
The peak RSS is the largest individual descendant reported by `time -v`, not
the sum of concurrent processes. These historical `wait4`-based RSS values may
also include a launcher's earlier high-water mark and are not memory budgets.

| Executor | Full-build median | Full-build range | Peak RSS range | Runs |
| --- | ---: | ---: | ---: | ---: |
| Samurai 1.3 | 551.53 s | 497.02–711.28 s | 371,596–380,280 KiB | 5 |
| Ninja 1.13.2 | 533.44 s | 506.31–670.03 s | 368,212–378,360 KiB | 5 |

The full-build result is inconclusive: paired differences ranged from
173.01 seconds in Samurai's favor to 204.97 seconds in Ninja's favor.

Five additional interleaved no-op runs used the selected executor binaries
and separate completed trees generated by the upstream bootstrap CMake.
Every run reported no work.

| Executor | No-op median | No-op range | Runs |
| --- | ---: | ---: | ---: |
| Samurai | 149.53 ms | 140.67–204.07 ms | 5 |
| Ninja | 101.01 ms | 84.21–144.09 ms | 5 |

Ninja's median was 32.4% lower. Each paired difference favored Ninja, ranging
from 46.55 to 70.77 milliseconds with a median of 53.34 milliseconds. Ninja is
selected because the paired gain exceeds 5% and the observed paired spread.
CMake generates linker dependency files for Ninja but not for Samurai. In a
separate `strace -c` diagnostic, file status calls dominated measured syscall
time for both executors; this does not explain all user-space runtime. Ninja
rejects Samurai's build log, so each executor needs its own completed tree.

The host had eight CPUs and another workload. The one-minute load at sample
boundaries ranged from 5.95 to 19.57. One upstream sample also overlapped a
small download of candidate aarch64 APKs. The owner waived the performance
gate; these results include that contention and should not be read as quiet-host
latency. Parallel compilation dominates the clean pipeline, while graph and
filesystem checks account for substantial no-op work.

The x86_64 Alpine CMake APK is 24,718,959 bytes. Adding its locked closure
increased the inspected builder image from 139,574,122 to 296,911,603 bytes.
The source-built, unstripped Ninja executable is 1,662,144 bytes; Samurai is
73,080 bytes. The comparison excludes the one-time executor builds, so the
additional Ninja build time is not separately measured. These are builder
inputs and are not staged in the distribution.

## Developer compiler cache

`build` uses the existing `kache` wrapper for C and C++ compilations, with a
persistent per-target store in `.work/compiler-cache/`. Compiler and build
inputs participate in the cache keys. Linker-only driver flags stay on link
commands, allowing compilations to be cached without changing their objects.
Qualification builds use a separate phase fingerprint and do not use this
compiler cache. Rust continues to use its existing wrapper.

A native x86_64 build completed the ELF audit with caching enabled. A repeated
compile of a CMake source was a local cache hit, ran no compiler, and restored
the original object bytes. A header-change probe produced a fresh object.
These checks establish cache behavior; they do not measure a speedup. Native CI
caches verified inputs, Rust phases, and qualification build phases. Those caches
do not enable the C and C++ compiler cache in qualification builds.

## Debug information

On the x86-64 candidate, LLVM's debug-only stripping reduced the executable
from 67,381,800 to 41,805,976 bytes. With the same staged resources, notices,
archive settings, and test metadata, the compressed archive changed from
14,366,104 to 10,168,980 bytes. These are exact sizes for the tested bytes;
the release archive also contains its own build metadata.

The debug-stripped candidate passed the ELF audit and the basic, network, and
parity suites. Stripping all symbols was rejected because it removed compiler
provenance needed by the audit. The staging change retains symbols and reruns
the audit on the stripped executable.

## Clean packages and unchanged qualification builds

Two clean x86-64 package builds for commit `91983ee` ran as part of the
reproduction check. They used separate worktrees and no developer C/C++ cache;
the builder image, downloaded inputs and Rust vendor/tool phases were already
available, and filesystem caches were warm. The package command includes
bootstrap, compilation, the basic acceptance suite and archive creation. It
finished in approximately 12 minutes 2 seconds and 11 minutes 5 seconds,
respectively; the milestone observer polled every five seconds. Both archives
had SHA-256
`25c2db75db95c35cea449f458a9da6f0123402e9cee6a4e2cc576f332af77b9b`.
From 17:50:32 UTC onward, the one-minute host load ranged from 2.76 to 11.25
on eight logical CPUs. The beginning of the first build was not observed for
load. These are two warm-filesystem observations, not cold-start measurements.

A separate warm test ran `build.py build --qualification-build` five times in
the completed experimental worktree at commit `46103c8`. The executable in
that tree matched the first clean `91983ee` build byte-for-byte. Each command
reported that the Rust static library and CMake phase were reused; it did not
use the developer C/C++ compiler cache. The median wall time was 25.916 s,
with a range of 25.458–32.031 s. Host load at the sample boundaries ranged
from 1.82 to 2.12. The command includes controller, integrity and container
work; this run did not separately time those components or measure aggregate
container RSS.

| Run | Wall seconds | Load before | Load after |
| --- | ---: | ---: | ---: |
| 1 | 32.031 | 1.82 | 1.88 |
| 2 | 25.458 | 1.88 | 2.12 |
| 3 | 26.017 | 2.12 | 2.07 |
| 4 | 25.677 | 2.07 | 2.10 |
| 5 | 25.916 | 2.10 | 2.06 |

The clean package and unchanged build are different commands at different
commits, so these observations are not a paired speedup. They measure the
cost of producing CMake, not Laputa provisioning or downstream project builds.

Two clean x86-64 builds at release commit `5932be3` produced the same file
tree and archive bytes. Their archive SHA-256 was
`cbab9ea823b0e1b609b7b3b273e6a9a8c89d3bfdb7aa382d380f880bf7f78e7c`,
which also matches the native CI and published x86-64 archive. A separate
ARM64 clean-build reproduction was not run.
